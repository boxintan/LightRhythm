# 检测计算优化（2026-11-26）

目标是降低检测本身的计算量，争取默认 1600 最长边预览在一秒内完成。耗时定义与页面一致：横纹与摩尔纹都完成后停止计时，不含照片读取/解码；设备基准另记录包括协程调度的调用墙钟时间，用较严格的墙钟时间检查预算。不同手机的绝对耗时仍需分别实测。

## 修改

- 局部扫描将完整排序替换为精确的顺序统计选择；单调取样直接取对应位置。复用亮度/取样数组，预计算倾斜坐标，并对已确认全不透明的窗口跳过重复的逐样本有限值检查。透明输入仍走原检查路径。
- 局部窗口只计算所需的周期与支持，不再为每次方向尝试构造整份行序列报告，或计算随后不会使用的整图相位支持。周期判据由整图与局部扫描共享，避免复制两套规则。
- 短序列用前缀矩筛选相关峰，长序列以零填充 FFT 加速滞后积。可能的峰、相邻项、半周期及短周期别名用原 Pearson 公式重算；退化方差回退原计算。保留保守的浮点筛选裕量，并测试阈值附近情况。
- 摩尔纹复用窗口工作区与平面拟合几何。对相同有效像素掩码，方向/滞后的像素配对只过滤一次，供各颜色表示复用；保持原有像素与求和顺序。全有效窗口的平方能量用分采样相位的前缀表查询，可能的峰及边界值再以原式复核。
- 两类检测以结构化协程并行读取同一稳定软件预览，各自拥有工作区；结果仍须全部完成后返回。并行改善墙钟延时，前述复用和搜索改善计算工作量，二者分别描述。

预览尺寸、窗口尺度、方向、幅度/相关门槛、空间证据约束均保持。未缓存某张照片的检测结论，也未引入超时后跳过检查的路径。方法版本保留 v10 / dual-v5，具体实现由 Git 提交区分。

## 正确性

对 01–20 的原尺寸及 1600/960/480 条件，共 75 条记录，序列化完整 `BandingResult` 与 `MoireResult` 后比较 SHA-256；包括所有行序列、浮点诊断数值、候选位置及其顺序，优化前后完全一致。08/11 是重复图片；这些是计算等价回归，不是泛化准确率验证。

新增单元检查覆盖精确分位数、单调/重复/随机取样、FFT 长度及阈值邻域、全部方向与采样相位、低能量区域、不同有效掩码及工作区跨窗口复用。Android 另检查并行结果与串行结果一致、源像素不变。此前 v10 的误报、漏检边界没有因本次性能优化而被重新标注。

## 设备测量

使用 API 37 的已有 Medium Phone 模拟器、独立 `.detectiontest` 调试包。每轮在新 instrumentation 进程先检测 20，再顺序检测 01–20 两遍：首次调用 1 条，后续 40 条。每次从文件重新解码到应用预览尺寸，解码不计时，检测结果每次重新计算；中途无额外预热图。08/11 重复，仅作为文件工作负载，不计为独立场景证据。

`DetectionPerformanceTest` 默认不加入功能回归；用 `runDetectionBenchmark=true` 显式启用，可选 `detectionBudgetMs=1000` 对所有调用（包括首次）断言小于一秒。未通过时保留失败记录和全部 CSV，不把“加快”写成“全部达标”。分阶段记录为串行诊断，不能拿阶段和冒充并行管线的实际延时。

本次同一模拟器、同一调试包配置的墙钟记录如下，单位毫秒。分位数采用后续 40 条调用的最近秩定义，首次为新 instrumentation 进程内的第一次调用，不代表清除系统编译缓存后的首次安装。

| 指标 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 进程首次调用（20） | 5744 | 1301 |
| 后续 40 条中位数 | 4624.5 | 534 |
| 后续 40 条 P95 | 8596 | 973 |
| 后续 40 条最大值 | 9831 | 1348 |
| 后续调用低于 1000 ms | 2/40 | 38/40 |

严格的一秒预算测试**没有通过**：首次 20 为 1301 ms，14 两次分别为 1348/1326 ms，其余 38 次后续调用低于一秒。不能宣称所有照片、首次调用或所有手机都已低于一秒。用户确认优先降低算法计算量，允许机型间存在差异；本轮交付计算优化，并保留这一未完全达成的时间边界。调试模拟器数据受宿主机负载影响，不替代实体机验收。

计算工作量的改善也体现在串行分阶段记录，而不只是并行收益。例如 20 的局部扫描由 2494 降至 239 ms，摩尔纹由 2668 降至 917 ms；07 的局部扫描由 2667 降至 270 ms。阶段记录用于定位和对照，不是跨手机性能承诺。

最终验证：108 项桌面算法/工具、125 项完整 App JVM 通过，无失败；范围重叠，不相加。APK、Android 测试 APK、lint 构建通过。功能仪器回归 51 项中 48 通过、0 失败、3 项正式包名更新测试按既有前提跳过；性能基准单独执行，其一秒断言失败不被混入“功能测试通过”。完整结果的 75 条 SHA-256 对照全部相同。

本机证据在忽略的 `build/detection-performance/`：优化前 `baseline-device.csv`、完整结果 `baseline-parity.csv`，最终工作区/不透明优化的 `opaque-device.csv`、`opaque-parity.csv`、`opaque-tests.txt`、`opaque-build.txt`、设备功能回归 `device-regression.txt`。中间版本的计时和预算失败也保留在该目录；照片和生成报告不提交。

复现最终设备基准（私有照片需先放入对应 App 文件目录）：

```powershell
adb shell am instrument -w -r -e class com.example.lightrhythm.DetectionPerformanceTest -e runDetectionBenchmark true -e detectionBudgetMs 1000 -e detectionSampleDirectory /data/user/0/com.example.lightrhythm.detectiontest/files/new-samples-v9 com.example.lightrhythm.detectiontest.test/androidx.test.runner.AndroidJUnitRunner
```

普通设备回归使用 `-e notClass com.example.lightrhythm.DetectionPerformanceTest`，以免混合功能测试与计时工作负载。桌面 `BenchmarkDetectionKt` 只用于定位开销，不代替手机验收。
