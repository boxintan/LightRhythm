# 从逐图回归转向共性判据：v10 审查（2026-11-26）

当前实现仍是周期纹理候选检测原型，尚无独立真实场景验证，不能作为已验证的通用横纹/摩尔纹分类器。单张 RGB 图中的真实物体纹理与成像干扰可能具有相同的周期统计特征；“周期明显”“几个位置同时出现”“单元测试通过”均不等于已经区分了成因。

## 本次失败及原有验证问题

用户提供 20 号正常百叶窗，v9 在未用过的场景上失败。桌面复现结果：1080×1920 原图不触发；应用 900×1600 预览触发摩尔纹、三个候选位置；540×960 触发局部横纹、12 个 256 窗口；270×480 触发摩尔纹、四个候选位置。Android 原图/预览行为另行验证。20 一旦用于修改算法即成为开发数据，不能在修改后继续把它当作独立验证样本。

v8 的透视持续性约束只改善了一类方向不一致的重复纹理；v9 的颜色区域提议只改善了一类小屏幕漏检，均没有建立通用的物体纹理/干扰区分能力。旧摩尔纹规则只检查颜色重复，现有 `straightColorTextureRemainsAnAmbiguousCandidate` 也明确保留普通直线彩色纹理可触发的情况。不能通过排除“所有百叶窗”来修复：物体类别不是有无成像干扰的标签。

旧批量评估仅统计横纹，没有摩尔纹的混淆矩阵；仅校验路径和组名，改名复制的相同照片可能重复计数。此前 01–19 已用于调参，08/11 还是完全相同的文件，因此照片尺寸记录数和测试数量都不是独立验证规模。

## 共性规则修正

### 1. 检查颜色周期是否只由归一化产生

旧颜色信号为 `255×(R−G)/(R+G+B)` 和 `255×(B−G)/(R+G+B)`。对带固定色偏的中性明暗纹理，例如 `RGB=(L+40,L+12,L)`，原始 R−G 恒定，但归一化分母随 L 周期变化，便会制造出颜色周期。这是变换带来的证据混淆，并不需要照片具有某个特定窗框或方向。

新规则同时检查两种表示：逐像素归一化色差，以及只用整块平均亮度缩放的原始色差。二者均去空间平面趋势并满足幅度 1.5；归一化表示先取得相关峰 0.65，原始色差在同一方向和周期也须达到相关 0.65，二者均要求半周期相关不高于 −0.25。仅由分母制造的周期不能成为摩尔纹候选；乘性固定色调则由归一化表示拒绝。增加 R−B，让三个 RGB 差分受到同样检查，不固定偏爱绿色参考通道。

没有把所有与亮度相关的颜色变化直接回归掉，因为这会同时抹掉真实彩色条纹。两种表示复核仍不能区分所有混合色偏、真实规则彩色内容和成像干扰，不能解释为通用成因识别。

保留 4×4 网格；未获得足够证据时独立尝试 6×6 网格，同样的窗口和门槛，不混合两轮的票数。它用于补偿更严格复核后的空间取样缺口，不放宽周期判据。`testedTiles` 是实际尝试的空间中心数（16，或 16+36=52），不是独立缺陷数。

### 2. 不把重复覆盖同一片像素当成多个位置

摩尔纹警报要求候选中存在三个来源矩形互不重叠的位置，原始 `tiles` 列表仍保留诊断候选。像素不重叠只是减少重复计数，不证明统计独立，也不证明存在三个真实干扰源。

局部横纹仍要求原来的跨行周期/倾斜持续性；另要求至少两列在 x 方向分离达到窗口边长的 2/3，各列的上下支持跨度也达到 2/3。按中心分析窗口计算，同轴两处的投影最多重叠 1/3，避免大窗口在窄图上高度重叠却获得多列支持。倾斜取样的预留边缘仍可能重叠；较窄的真实灰色局部条纹可能被保守拒绝。

版本为 `row-region-periodicity-v10` / `row-region-broad-v10`、`local-chroma-dual-v5`。没有按文件名、图片哈希、固定窗框坐标或照片编号分支。现有区域字段、坐标及修复阻断语义保持。

## 验证原则及证据

新增测试覆盖一组固定色偏的中性周期纹理（不同周期和倾斜）、JPEG 编码与预览缩放、相互重叠的候选、窄区域大窗口重复计票；同时检查独立彩色细纹在亮度变化、色偏和 RGB 通道互换下保持检出。它们是受控模型回归，不是未见真实场景的准确率验证。

将新增测试与原算法隔离运行，四项回归在原算法上失败：中性色偏纹理、JPEG/缩放后的中性纹理、重叠摩尔纹计票、窄区域局部计票；当前算法通过。失败日志和隔离副本仅在本机 `build/generalization-audit/legacy-check/`，不改动 Git 主分支。完整构建及设备结果在下方更新。

最终验证：桌面算法/工具 104 项、完整 App JVM 121 项通过（范围重叠）；debug APK、Android 测试 APK、lint 构建通过。API 37 / Android 17 运行 50 项仪器用例，按状态码统计为 47 通过、0 失败、3 跳过。跳过的是要求团队正式包名的 `AppUpdateArchiveTest`，本轮使用独立 `.detectiontest` 包，不将跳过项记为通过。仪器运行器末尾输出 `OK (50 tests)`。

20 在 Android 1920/1600/960/480 最长边下不触发两类警报，Bitmap 和源文件不变；导入页面不显示误报，点击修复不生成结果。13、09、小屏幕、旋转、导入保存及已有颜色正例 03/07/08/10/12 的三种预览尺寸回归保持通过。

桌面 20 张照片的 75 条尺寸记录中，横纹状态只有 20/960 从误报变为未触发；其他旧横纹状态保持。摩尔纹方面，20/1600、20/480 不再触发，原有 03/07/08/10/12 的尺寸候选保持；17 原图的旧候选不再触发。**17/480、18 原图及 18/960 新增摩尔纹候选，缺少明确的摩尔纹阴性/阳性标签，不能计为成功，也不能忽略其误报风险。** 这些变化体现了当前“颜色周期候选”和真实干扰分类之间仍存在的缺口。15/16 继续漏检，18/480 与 19/960、19/480 仍有原来的横纹漏检。

## 评估流程修正

清单增加可选 `moireLabel`，横纹和摩尔纹分别标注 `banding/clean/unknown` 与 `moire/clean/unknown`，旧五列清单兼容；缺失的摩尔纹标签是 unknown，绝不当成正常样本。两个目标各自统计 TP/FP/TN/FN、误检率、召回率与评估覆盖率，增加按场景/来源组汇总。

读取时校验 SHA-256，完全相同的文件即使改名也不能重复计数。哈希不能识别重新压缩、缩放、裁剪或同场景连拍，仍须人工放入同一 source/capture group。输出保存清单哈希和分组规模，防止标签、样本组成变化被遗漏；工具无法自动证明 validation 独立。

现有照片全部归 dev；去重后 19 个文件，包括 20。只使用用户明确给出的标签，其余保留 unknown。独立 validation 为空，相关指标留空，不把“开发集没有新增误报”包装成泛化准确率。后续真实验证应覆盖多个百叶窗、栅栏、砖墙、织物、文字、屏幕、反射及不同设备/压缩来源；调参前冻结来源组，固定算法后再查看未见组。一旦用某个验证失败来改代码，该来源组转入 dev，并另取未见组评估下一版。

另以最长边 1600 的实际应用预览条件运行评估（`-EvaluationMaxEdge 1600`），保留原图与预览两种条件的区分；不将尺寸副本算成新的独立图片。当前明确标签仅够评估七个横纹目标、三个摩尔纹目标，因此报告中的开发集比例也不适合推广。清单、报告和照片不上传；本机 `build/generalization-audit/` 保存 `photo20-before.csv`、`after-final.csv`、`legacy-regressions.txt`、`final-evaluation-tests.txt`、`app-preview-final/`、`gradle-validation.txt` 和 `device-tests.txt`。
